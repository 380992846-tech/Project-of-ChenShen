# KV Cache 推理优化报告

## 环境
- 设备：`cuda`（NVIDIA A800 80GB）
- 模型：decoder-only GPT，参数 `891,648`
- 配置：`n_layer=4`, `n_head=4`, `n_embd=128`
- 其他：`block_size=512`, `vocab=256`
- 实验：prompt 长度 `64`，生成 `128` 个 token

## 结论
| 指标 | 无 KV Cache | 有 KV Cache |
|------|------------|-------------|
| 解码总耗时 (s) | 0.4322 | 0.5896 |
| 平均每 token 耗时 (ms) | 3.377 | 4.606 |
| 生成速率 (tokens/s) | 296.1 | 217.1 |
| **加速比** | 1.0× | **0.73×** |

- prefill 耗时（一次性处理 prompt）：`2.42 ms`

## 说明
- 无 KV Cache 时每步都要对全部历史 token 重新做一次注意力，单步耗时随序列增长（O(T)）。
- 有 KV Cache 时 K/V 在 prefill 阶段算好并缓存，decode 每步只处理 1 个新 token（O(1)），
  单步耗时近似恒定，总耗时随生成步数**线性**而非**平方**增长。

## ⚠️ 关键观察：GPU + 小模型下不升反降（0.73×）
本次在 **A800 GPU + 891K 小模型 + 短序列（64 → 128）** 下，加入 KV Cache **反而更慢**：

- GPU 专为**并行重算**设计，小模型单步重算速度极快，重算整个序列的成本很低；
- 而本实现每步需做 `seq[:, -1:]` 切片 + past 索引 / 拼接，KV Cache 的**显存读写与张量搬运开销**
  **超过了**重算收益，因此出现负优化；
- 对比 **CPU** 上运行同一模型（prompt 128 / gen 300）：重算 O(T) 是串行、代价高，KV Cache 优势
  明显（**3.57×**）。

> **结论**：KV Cache 的复杂度优势（O(T)→O(1)）要在**长序列 / 大模型 / CPU** 等"重算代价高"的场景才兑现；
> 在 **GPU + 小模型 + 短序列**下可能因 cache 管理开销反成负优化。这正说明**优化并非免费午餐**——
> 需结合硬件特性与规模评估，而非盲目套用。真实加速比还取决于显存带宽、批大小与算子实现
> （如 FlashAttention / vLLM 的页式 KV Cache）。
