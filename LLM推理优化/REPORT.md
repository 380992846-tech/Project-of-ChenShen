## 实验环境

- **设备**：CPU（本仓库实验为算法正确性与可复现性优先）
- **模型**：decoder-only GPT，多种规格（891K / 237K / 187K / 984K 参数）
- **依赖**：PyTorch、NumPy

> 所有加速均为**算法层**收益；真实的 GPU 加速比还取决于显存带宽、批大小与算子实现（如 FlashAttention / vLLM）。

## Step 1 · KV Cache

**模型**：decoder-only GPT，参数 `891,648`，`n_layer=4`、`n_head=4`、`n_embd=128`、`block_size=512`、`vocab=256`。
**实验**：prompt 长度 `128`，生成 `300` 个 token。

| 指标 | 无 KV Cache | 有 KV Cache |
|------|------------|-------------|
| 解码总耗时 (s) | 3.0126 | 0.8428 |
| 平均每 token 耗时 (ms) | 10.042 | 2.809 |
| 生成速率 (tokens/s) | 99.6 | 356.0 |
| **加速比** | 1.0× | **3.57×** |

- prefill 耗时（一次性处理 prompt）：`9.56 ms`

### 分析
- 无 KV Cache 时，每一步都要对全部历史 token 重新做一次注意力，单步耗时随序列增长（O(T)）。
- 有 KV Cache 时，K/V 在 prefill 阶段算好并缓存，decode 每步只处理 1 个新 token（O(1)），单步耗时近似恒定，总耗时随生成步数**线性**而非**平方**增长。
- 本报告用随机权重模型演示**算法层面的复杂度差异**；真实加速比还取决于显存带宽、批大小与算子实现。

## Step 2 · 权重量化

**模型**：字符级 GPT，`237,312` 参数，训练 300 步；训练文本 10 KB，评估文本 12 KB。

| 精度 | 权重存储 (MB) | 权重复原误差 | logit 偏差 | PPL |
|------|---------------|--------------|------------|-----|
| FP32 | 0.905 | 0.00e+00 | 0.00e+00 | 414.44 |
| INT8 | 0.234 | 1.70e-02 | 6.81e-03 | 414.40 |
| INT4 | 0.178 | 2.09e-01 | 4.63e-02 | 415.93 |
| FP8 | 0.234 | 1.79e-01 | 1.87e-02 | 414.72 |

**运行时解码延迟（真实 int8 算子）**：

| 模型 | 解码 (ms/tok) |
|------|---------------|
| FP32 | 1.07 |
| INT8 (torch 动态量化) | 3.53 |

### 分析
- **存储**：FP32 → INT8/FP8 约 **4×** 压缩，INT4 约 **5×**。
- **质量**：各精度 PPL 几乎不变（≈414），INT8 的 logit 偏差最小。
- **运行时效**：CPU 上 torch 动态 INT8 对小模型反而更慢（动态激活量化有固定开销）；真正的 INT8/INT4 加速需 **weight-only + 融合算子**（GPU 上的 Marlin / Triton 等）。
- INT4/FP8 为 weight-only（计算用反量化权重），度量的是权重精度损失与存储节省。

## Step 3 · 投机解码

**模型**：target `984,192` 参数；draft `60,480` 参数。生成 `96` token，γ=4，3 轮取平均。

| 方式 | 吞吐 (tokens/s) | 每 token 的 target 前向次数 |
|------|-----------------|------------------------------|
| target (KV cache) | 255.8 | 1.00 |
| speculative | 243.0 | **0.20** |

- **墙钟加速比**：0.95×（CPU 小模型，波动较大）
- **平均每轮接受草案数**：**5.00**（最高 γ+1=5）

### 分析
- 投机解码用更快的 draft 一次预测 γ 个候选，target 一次性并行验证；接受率越高，每轮 target 前向产出的 token 越多。
- **每 token 的 target 前向次数**从 1.0 降到 0.20 —— 这是与 GPU 无关的**算法层收益**，在真实大模型上直接对应 ~5.0× 的 target 计算量下降。
- 墙钟加速取决于 **draft 相对 target 的加速比 × 接受率**；draft 不够快（如 CPU 小模型）时墙钟收益有限且噪声大。
- 正确性由精确拒绝采样保证（draft==target 时输出与 target 完全一致，测试覆盖）。

## Step 4 · 批量/连续批处理

### 4.1 批量解码（`serving.py`）

**模型**：`187,328` 参数；请求数 `48`，prompt `16`，生成 `32`，3 轮平均。

| batch size | 吞吐 (tokens/s) | P50 (ms) | P99 (ms) |
|-----------|-----------------|----------|----------|
| 1 | 269.5 | 119.3 | 213.3 |
| 4 | 956.4 | 143.3 | 212.2 |
| 8 | 2092.9 | 129.3 | 139.6 |
| 16 | 4379.0 | 115.9 | 136.0 |

- 增大 batch 显著提升吞吐（摊薄单步前向固定开销）。
- 代价是单请求延迟上升（吞吐 vs 延迟权衡）——这正是 serving 系统要平衡的指标。

### 4.2 Continuous Batching（`continuous.py`）

**模型**：`187,328` 参数；请求 `64`，prompt `16`，长度均匀分布 `[2,30]`；有效 token 总数 `1038`。

| 调度方式 | 墙钟 (s) | 有效吞吐 (tokens/s) |
|---------|----------|---------------------|
| sequential | 3.031 | 342 |
| static batch | 0.517 | 2008 |
| **continuous batching** | 0.817 | **1271** |

### 分析
- **continuous batching 远超串行**（~4×），并正确实现了动态 slot 复用（输出与逐条解码完全一致，测试覆盖）。
- 本 CPU 玩具基准里 static 略胜 continuous，是因为小模型 + 短序列下 static 的紧凑缓存没有 padding/克隆开销，尾部浪费也小。
- continuous 的真正优势在 **GPU + 长序列 + 长度高方差 + 稳定请求流 + PagedAttention 式高效显存分配** 场景下才完全释放（本实现用朴素 padded 缓存演示 slot 复用语义）。
- 本实现重点在**正确性**（slot 复用语义）与相对串行的收益；要测出相对 static 的优势，需配合 PagedAttention 的按块分配（见 Roadmap）。

## 总结与局限

### 成果
| 优化 | 算法层收益 |
|------|-----------|
| KV Cache | O(T²) → O(T)，实测 3.57× |
| 量化 | 存储压缩 4–5×，PPL 无损 |
| 投机解码 | target 前向降到 0.2 次/token |
| 批量/连续批处理 | 吞吐随 batch 近线性增长；continuous batching 相对串行 ~4× |

### 局限与后续
- 所有实验在 **CPU 小模型**上运行，目的是验证**算法正确性与可复现性**，而非 GPU 峰值性能。
- 真实生产级加速需要：**PagedAttention**（按块 KV 分配省显存）、**融合算子**（Marlin / FlashAttention / Triton）、weight-only 量化的真实算子加速。
- 墙钟收益（尤其投机解码）受 draft 加速比与硬件影响，应在目标 GPU + 真实模型上复测。
